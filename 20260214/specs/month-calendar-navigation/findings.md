| Decision                             | Rationale                                  |

## Issues Encountered

### 1. OpenAPI 섹션 제거

**문제**:

OpenAPI Specification 섹션이 UI-only 기능과 맞지 않음.

**원인**:

템플릿이 기본적으로 API 문서를 포함하도록 되어 있었음.

**해결**:

OpenAPI Specification 섹션을 삭제.

**결과**:

요구사항 문서가 UI 기능에 맞게 정리됨.

### 2. Vitest와 Playwright 스펙 충돌

**문제**:

Vitest가 `tests/e2e`를 수집하면서 Playwright `test.beforeEach`가 실패함.

**원인**:

E2E 테스트가 Vitest 수집 대상에 포함되어 있었음.

**해결**:

Vitest include/exclude로 `tests/e2e`를 제외하고 `tests/units`를 분리함.

**결과**:

`npm test`와 `npm run test:e2e`가 충돌 없이 병행됨.

### 3. jsdom 28 버전 ESM 호환성 이슈

**문제**:

jsdom 28.0.0에서 `require() of ES Module` 오류 발생으로 모든 단위 테스트가
실패함.

**원인**:

jsdom 28의 의존성인 `@exodus/bytes/encoding-lite.js`가 ESM이지만 CJS로
require되어 호환성 문제 발생.

**해결**:

jsdom을 제거하고 happy-dom 20.6.1로 교체.

- `package.json`: jsdom 제거, happy-dom 추가
- `vite.config.ts`: `environment: "jsdom"` → `"happy-dom"`

**결과**:

모든 단위 테스트(9개) 정상 통과, happy-dom이 더 가볍고 빠름.

## Learnings

### 기본 기능 범위 정리 (2026-02-14)

월간 달력 표시, 월 이동, 오늘 이동에 범위를 제한했다. 첫 구현은 핵심 가치만
추출하면 빠르게 완성하고 피드백을 받을 수 있다. 기능을 추가하는 건 언제든
가능하지만, 범위를 줄이는 건 어렵다.

### API 필요 없음 명시 (2026-02-14)

spec에서 API 없이 클라이언트만으로 구현하는 기능임을 명시했다. 구현 범위와
책임이 명확해지면 불필요한 백엔드 작업을 피할 수 있다. UI 전용 기능은 OpenAPI
같은 API 문서 섹션을 제거하면 문서가 간결해지고 혼란이 줄어든다.

### 계획 단계 정리 (2026-02-14)

Outside-in 순서와 TDD 흐름을 plan.md에 반영하고, tasks/progress 작성 단계에
진입했다. 계획 문서에 순서를 명시하면 구현 중 방향성을 잃지 않고 일관된 흐름을
유지할 수 있다. 특히 TDD의 Red-Green-Refactor 사이클을 명시하면 각 단계에서
무엇을 해야 하는지 명확해진다.

### 초기 설정 완료 (2026-02-14)

Vite + React + TypeScript + Tailwind + Vitest/RTL + Prettier를 기본 툴체인으로
설정했다. Node 버전은 `.nvmrc`로 고정했다. 이 조합은 빠른 개발 환경(Vite), 타입
안정성(TypeScript), 빠른 스타일링(Tailwind), 안정적인 테스트(Vitest/RTL), 일관된
포맷팅(Prettier)을 동시에 확보할 수 있다. `.nvmrc`로 Node 버전을 고정하면 팀원
간 환경 차이를 줄이고 CI/CD 일관성을 보장한다.

### UI 규칙 확정 (2026-02-14)

주 시작 요일은 일요일로 고정하고, 오늘 버튼은 상단 오른쪽에 "오늘" 라벨로
배치하기로 결정했다. UI 규칙을 미리 결정하면 구현 중 고민이 줄고 일관된 UX를
제공할 수 있다. 나중에 바꾸는 것보다 처음에 정하는 게 훨씬 쉽다.

### 문서 운영 규칙 재확인 (2026-02-14)

`Test Results`는 최신 상태 1행만 갱신하고, `Error Log`는 모든 오류를 누적
기록한다. 역할을 분리하면 현재 상태와 문제 이력을 동시에 관리할 수 있다. 각
문서의 갱신 규칙(갱신 vs 누적)을 명확히 정의하면 실패 기록이 많아도 진행 상황은
명확하게 유지된다.

### 모호한 체크박스 제거 (2026-02-15)

범위가 불명확한 "초기 컴포넌트/유틸 파일 구조 확정" 항목을 제거하고 명확한
체크박스만 유지했다. 구체적이고 완료 기준이 명확한 항목만 남기면 진행률을 정확히
측정할 수 있다. 애매한 체크박스는 완료 판단을 어렵게 만들고 진행률을 왜곡한다.

### Outside-in 첫 연결 (2026-02-15)

App에서 MonthCalendar를 먼저 연결해 사용자 진입점을 확보했다. 사용자
진입점(App)부터 시작해 필요한 컴포넌트를 점진적으로 연결하면 사용자 흐름이 먼저
보장되고 과도한 구현을 방지할 수 있다. 초기 피드백 루프가 빨라져 방향을 빠르게
조정할 수 있다.

### MonthCalendar 기본 렌더 완료 (2026-02-15)

연월 표시, 요일 헤더, 오늘 강조가 포함된 기본 월간 그리드를 구성했다. 한 번에
모든 기능을 구현하지 않고 기본 화면부터 완성하면 진행 상황을 눈으로 확인할 수
있어 동기부여가 된다.

### CalendarHeader 버튼 동작 구현 (2026-02-15)

이전/다음/오늘 버튼이 기준 월을 변경하도록 상태를 추가했다. 버튼을 먼저 배치하고
동작을 나중에 연결하는 것보다, 동작과 함께 구현하면 테스트하기 쉽다.

### CalendarGrid 분리 (2026-02-15)

달력 그리드 렌더링을 `CalendarGrid` 컴포넌트로 분리해 역할을 명확히 했다. 각
컴포넌트의 역할이 명확해지면 유지보수가 용이해진다. 하나의 컴포넌트가 여러 가지
일을 하면 테스트와 수정이 모두 어려워진다.

### 달력 유틸 분리 (2026-02-15)

월 라벨, 이전/다음 월 이동, 월간 그리드 생성 로직을 `src/lib`로 분리했다. UI
컴포넌트(`src/components`)와 계산 로직(`src/lib`)을 분리하면 테스트가 쉬워지고
로직 재사용성이 높아진다. 순수 함수로 분리된 로직은 UI 없이도 테스트할 수 있다.

### 상태 기준일 분리 (2026-02-15)

`today`와 `baseDate`를 분리하면 "오늘" 복귀와 현재 월 표시가 충돌하지 않는다. 월
이동은 항상 `baseDate`만 변경하고, `today`는 고정한다. 하나의 상태로 두 가지
역할을 처리하려고 하면 로직이 복잡해지고 버그가 생긴다.

### 달력 그리드 계산 규칙 (2026-02-15)

주 시작 요일이 일요일이면 그리드 시작/끝 날짜를 주 단위로 맞춰야 한다. 경계
월(12월↔1월) 테스트를 먼저 정의하면 그리드 계산이 흔들리지 않는다. 일반적인
케이스보다 경계 조건을 먼저 테스트하면 로직의 안정성을 빠르게 확보할 수 있다.

### 빌드 설정 보정 (2026-02-15)

`vite.config.ts`에서 `vitest/config`를 사용해 build 타입 오류를 해결했다. test
옵션 타입 체크가 활성화되어 설정 오류를 사전에 방지할 수 있다. `defineConfig`를
어디서 import하느냐에 따라 타입 검증 범위가 달라진다.

### 테스트 안정성 패턴 (2026-02-15)

`vi.useFakeTimers()`와 사용자 입력 시뮬레이션 조합은 대기 타임아웃을 유발할 수
있다. 단순 클릭 검증에는 `fireEvent`가 더 안정적이며, 필요 시 `userEvent`는 별도
기준을 둔다. 테스트가 불안정하면 개발 속도가 느려지고 신뢰도가 떨어진다.

### 검증 3회 원칙 적용 (2026-02-15)

검증을 3가지 다른 관점으로 수행했다. 첫째, 단위 테스트로 개별 함수와 컴포넌트
동작을 검증했다. 둘째, E2E 테스트로 사용자 시나리오를 검증했다. 셋째, 빌드
성공으로 타입 안정성과 번들링을 검증했다. 같은 테스트를 반복하는 게 아니라 각기
다른 레벨에서 검증하면 놓치는 오류가 줄어든다.

### 수동 테스트 자동화 (2026-02-15)

Playwright E2E 테스트로 수동 테스트 시나리오를 자동화했다. 수동 테스트를 E2E로
고정하면 회귀 확인 비용이 크게 줄어든다. 수동 시나리오가 곧 자동화 스펙이 되어
문서와 테스트가 일치한다.

### 자동화 가치 (2026-02-15)

Playwright E2E 테스트는 수동 테스트 절차를 코드로 표현한 것이므로 문서 역할도
겸한다. 테스트 코드를 읽으면 어떻게 사용해야 하는지 알 수 있다.

### 문서/지침 동기화 (2026-02-15)

수동 테스트 자동화 내용을 지침과 스펙, README에 반영했다. 문서와 코드가 항상
일치하면 새로운 팀원이 합류했을 때 혼란이 없다.

### 문서 언어 설정 (2026-02-15)

한국어 콘텐츠가 중심인 앱은 `html`의 `lang`을 `ko`로 맞추는 것이 접근성과 SEO에
유리하다. 스크린 리더가 올바른 언어로 읽어주고, 검색 엔진이 언어를 정확히
인식한다.

### 테스트 디렉터리 분리 (2026-02-15)

Vitest는 `tests/e2e`를 제외하고 unit 테스트만 수집하도록 설정했다. E2E는
Playwright가 `tests/e2e`만 실행하도록 유지했다. 각 테스트 러너가 자신의 영역만
실행하도록 설정하면 실행 속도가 빨라지고 오류 추적이 쉬워진다.

### 테스트 결과 분류 확장 (2026-02-15)

Test Results는 테스트 종류와 레이어 기준을 함께 기록하도록 확장했다. UI
컴포넌트/유틸/단위/통합/E2E로 테스트를 분류하면 어느 레이어가 검증되었는지
명확히 파악할 수 있다. 테스트 결과를 분류하면 어떤 부분이 부족한지 한눈에
보인다.

### 테스트 환경 교체 (2026-02-15)

jsdom 28 버전의 ESM 호환성 문제로 happy-dom으로 교체했다. happy-dom이 더 가볍고
빠르며 최신 Vitest와 안정적으로 동작한다. 최신 버전이 항상 좋은 건 아니며,
때로는 대안을 빠르게 선택하는 게 문제 해결에 효율적이다.

## 프로젝트 회고 (2026-02-15)

### 프로젝트 개요

월간 달력 기본 보기 및 이동 기능을 Outside-in TDD 방식으로 구현했다. 2일간
(2026-02-14~15) 진행했으며, 요구사항 정의부터 구현, 테스트, 문서화까지 전체
워크플로우를 완료했다.

### 주요 성과

**완료한 기능**:

- 오늘 날짜 기준 이번 달 달력 표시
- 이전/다음 달 이동
- 오늘로 돌아가기
- 오늘 날짜 강조 표시

**작성한 문서**:

- README, spec, plan, tasks, progress, findings 6개 템플릿 문서 완성
- 모든 문서가 코드와 동기화된 상태 유지

**테스트 커버리지**:

- 단위 테스트 9개 (UI 컴포넌트 6개, 유틸 3개)
- E2E 테스트 3개 (초기 렌더, 월 이동, 경계 조건)
- 빌드 성공

**기술 스택 확립**:

- Vite + React + TypeScript + Tailwind + Vitest/RTL + Prettier
- E2E 자동화 (Playwright)
- Node 버전 고정 (.nvmrc)

### 어려웠던 점

**jsdom 28 ESM 호환성 이슈**:

의존성 설치 직후 모든 단위 테스트가 실패했다. `require() of ES Module` 오류였고,
jsdom 28의 내부 의존성 문제였다. happy-dom으로 빠르게 교체해서 해결했다. 최신
버전이 항상 안정적인 건 아니라는 교훈을 얻었다.

**테스트 러너 충돌**:

Vitest가 Playwright 스펙을 수집하면서 `test.beforeEach` 오류가 발생했다.
include/exclude 설정으로 영역을 명확히 분리해서 해결했다. 테스트 디렉터리 구조를
미리 설계하면 이런 문제를 예방할 수 있었을 것이다.

**문서 작성 균형**:

findings.md를 작성하면서 "얼마나 자세히 써야 하는가"를 고민했다. 너무 간결하면
맥락이 사라지고, 너무 자세하면 읽기 어렵다. 결국 "무엇을, 왜, 어떤 가치"를 모두
담되 3문장 이내로 정리하는 방식을 찾았다.

### 가장 큰 배움

**Outside-in TDD의 효과**:

사용자 진입점(App)부터 시작하니 기능이 동작하는 모습을 바로 확인할 수 있었다.
컴포넌트를 먼저 만들고 나중에 조립하는 것보다 훨씬 동기부여가 되고 방향성이
명확했다.

**검증 3회 원칙**:

같은 테스트를 3번 반복하는 게 아니라, 단위/E2E/빌드라는 서로 다른 레벨에서
검증하니 각 레이어의 오류를 빠짐없이 잡을 수 있었다. 한 가지 방법으로만 검증하면
특정 유형의 오류를 놓치게 된다.

**문서와 코드의 동기화**:

수동 테스트 시나리오를 E2E로 자동화하고, 그 내용을 README와 spec에 반영하니
문서와 코드가 저절로 일치했다. 문서를 별도로 관리하면 금방 어긋나지만, 코드로
표현하면 항상 최신 상태를 유지할 수 있다.

### 개선할 점

**초기 환경 설정 검증**:

프로젝트 시작 시 의존성을 설치하고 바로 테스트를 돌려봤어야 했다. jsdom 이슈를
더 일찍 발견할 수 있었을 것이다. 다음에는 "환경 설정 → 즉시 검증" 순서를
습관화하겠다.

**경계 조건 우선 테스트**:

12월↔1월 경계 조건을 나중에 테스트했는데, 계획 단계에서 먼저 정의했다면 구현이
더 안정적이었을 것이다. 다음에는 경계 조건을 먼저 테스트 케이스로 작성하고
구현을 시작하겠다.

**체크박스 완료 기준 명확화**:

"초기 컴포넌트 구조 확정" 같은 모호한 체크박스 때문에 완료 판단이 애매했다.
처음부터 "무엇을 했을 때 완료인가"를 명확히 정의한 체크박스만 만들어야 한다.

### 결론

File-based Planning Workflow를 처음부터 끝까지 완주했다. 문서 작성이 부담스러울
수 있지만, 진행하면서 문서가 나침반 역할을 했다. 특히 findings.md는 단순 기록을
넘어 재활용 가능한 지식 자산이 되었다.

Outside-in TDD는 사용자 관점을 놓치지 않게 해주고, 과도한 구현을 방지했다.
검증을 3가지 관점(단위/E2E/빌드)으로 수행하니 안정성이 크게 높아졌다.

가장 큰 성과는 "작동하는 소프트웨어"와 "동기화된 문서"를 동시에 얻은 것이다.
코드만 있으면 6개월 후에 맥락을 잃지만, 문서가 있으면 언제든 다시 시작할 수
있다.
